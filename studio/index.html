Case study A · Evidence-based digital asset research

Objective: help individuals understand established digital assets through structured, evidence-based research rather than social media hype.

How each engagement ran

  1. Objectives. Understand what the client wanted to learn and why.
  2. Scope. Shortlist established projects relevant to those objectives.
  3. Evidence. Gather fundamentals and market data: utility, adoption, market capitalisation and trading volume.
  4. Organise with AI. Use AI tools to structure notes and compare projects side by side.
  5. Validate. Check every AI-organised point against reliable primary sources: official documentation, block explorers and established data providers.
  6. Summarise. Deliver a research summary with risk considerations, so the client makes their own decision.

Deliverables

  • Research summaries and side-by-side comparisons
  • Risk considerations for each asset
  • A reusable research framework (see the research framework prototype)

Scope note: this was education and research support. I did not give personalised investment advice, manage client funds or promise returns. Clients made their own decisions.

Independent workflow

AI-assisted operational tracking

A method for managing a growing volume of records arriving from several sources, first used to run my own application tracker.

  1. Intake: capture incoming records
  2. Extraction: pull out the key fields
  3. Classification: assign a status
  4. Validation: flag duplicates and inconsistencies
  5. Tracking: keep one central tracker
  6. Reporting & follow-up: summarise progress and list what needs attention

The same pattern applies to incident tracking, ticket triage and exception management. No personal data is shown here.

Independent workflow

AI-assisted market monitoring

Exception-based monitoring: check on a schedule and only alert when something crosses a defined rule.

  1. Watchlist: define the assets to monitor
  2. Schedule: run checks at a fixed frequency
  3. Thresholds: define what counts as a significant move
  4. Alerts: notify only when a rule is met
  5. Validation: cross-check against a second source before acting

The same design suits finance exception monitoring: scheduled checks, thresholds and clear escalation.

Demo 1 · Bank-to-ledger reconciliation

A synthetic November bank statement and general ledger cash extract for a fictional Malaysian company. The data is deliberately messy: different date formats, currency text in amounts, inconsistent references and some planted problems. You can edit either CSV and run it again.

Rules: dates normalised to ISO (YYYY-MM-DD); amounts stripped of currency text and thousands separators, brackets read as negative; references normalised (e.g. "INV 00102", "inv-102" and "INV102" all become INV102). Match on reference first, then on exact amount within 3 days for items with no reference.

SOP and escalation note
  1. Run the reconciliation after the bank statement and ledger extract for the period are both final.
  2. Clear exact matches. Matches on amount and date only (no reference) go to a reviewer, not straight to cleared.
  3. For each exception, record the suggested category, owner and target date. Do not post adjusting entries from this tool.
  4. Bank-only items (fees, interest, unidentified receipts): the accountant prepares the entry with evidence; a second person approves it (maker-checker).
  5. Possible duplicates and amount mismatches: hold related payments and confirm against source documents before any reversal.
  6. Escalate to the finance controller when an item stays open past the close deadline, exceeds the agreed materiality threshold, or a duplicate payment is confirmed.
  7. A reviewer signs off the reconciliation and the exception list is kept as audit evidence.

Demo 3 · Master data validation

Two synthetic datasets, set up like a data migration: a legacy system extract and a new system load file, each holding vendors, customers and account codes, plus a few open transactions in the load file. The checks look for missing fields, duplicates (including near-duplicate names), inconsistent values and differences between the two files.

Validation rules used (simplified for the demo)
  • Required fields: vendors and customers need id, name, tax_id, country, currency; vendors also need bank_account; account codes need code, name, type, status.
  • Tax ID format (synthetic rules): MY = "C" + 10 digits; SG = 9 digits + letter; HK = 8 digits.
  • Currency must be a valid ISO code from the list in use, and is expected to match the country (MY=MYR, SG=SGD, HK=HKD, US=USD); a mismatch is a warning to verify, not an error.
  • Duplicates: same tax ID, or names that match after removing punctuation and company suffixes, or names at least 85% similar.
  • Transactions must not post to an inactive account code or reference an unknown vendor.
  • Cross-file: records missing from the load file, and changed bank accounts (a changed bank account needs independent verification before go-live).
